Разработка вдвоём — это отлично, так как можно разделить проект на две независимые, но взаимосвязанные части. Чтобы вы оба попрактиковались в Go, но при этом не мешали друг другу (не ловили merge-конфликты каждый день), предлагаю разделить зоны ответственности по **доменам**.

В системах связи есть два главных понятия:
1.  **Signaling (Сигналинг)** — управление комнатами, юзерами, текстовый чат и передача служебных данных (кто кому звонит). Это классический веб/вебсокеты.
2.  **Media (Медиа)** — сам SFU-сервер, который принимает и раздает пакеты голоса и видео через WebRTC.

---

### Роли в команде

**Разработчик 1 (Назовем его "Мастер Сигналов"):**
*   **Опыт:** Ему будет проще стартовать, так как это похоже на FastAPI.
*   **Ответственность:** HTTP API, База Данных, WebSocket-сервер (управление комнатами и пользователями).
*   **Технологии:** Go (Echo/Fiber), PostgreSQL/SQLite, `gorilla/websocket`.

**Разработчик 2 (Назовем его "Повелитель Медиа"):**
*   **Опыт:** Будет хардкорно изучать сетевые протоколы, WebRTC и работу с потоками в Go.
*   **Ответственность:** SFU-сервер для аудио и видео, интеграция TURN-сервера.
*   **Технологии:** Go (Pion WebRTC), Coturn (Docker), работа с RTP-пакетами.

*Фронтенд (Браузерную часть) можно поделить так: Разработчик 1 делает UI, кнопки и логику вебсокетов, а Разработчик 2 пишет JavaScript-логику для микрофона и экрана (`RTCPeerConnection`).*

### Подробный план разработки (Roadmap)

#### Этап 0: База и Инфраструктура (Неделя 1)
Цель: Подготовить почву, чтобы каждый мог писать свой код.
*   **Вместе:**
    *   Создать репозиторий на GitHub.
    *   Выбрать фреймворк для фронтенда (советую **React + Vite** или просто чистый JS + HTML/Tailwind, чтобы не усложнять).
*   **Разработчик 1 (Сигналы):**
    *   Поднять базовый HTTP-сервер на Go (Echo).
    *   Настроить подключение к БД (можно начать с SQLite, чтобы не мучиться с настройкой базы, для ваших нужд её хватит за глаза).
    *   Сделать эндпоинты: POST `/room` (создать комнату), GET `/room/:id` (проверить, есть ли комната).
*   **Разработчик 2 (Медиа):**
    *   Изучить архитектуру **SFU**.
    *   Склонировать примеры библиотеки `pion/webrtc` (особенно пример `sfu-ws` или `broadcast`).
    *   Написать изолированный Go-скрипт, который просто умеет принимать аудио-трек и отдавать его обратно.

#### Этап 1: Текстовый чат и WebSocket-роутер (Неделя 2)
Цель: Люди могут зайти по ссылке в комнату и видеть друг друга.
*   **Разработчик 1:**
    *   Пишет WebSocket-хаб на Go. В Go это делается через `map[string]*websocket.Conn` и горутины (смотри пример чата в доках `gorilla/websocket`).
    *   Логика: Юзер подключается -> заносится в мапу комнаты -> сервер рассылает всем `{"type": "user_joined", "user": "Vanya"}`.
    *   На фронте делает простую формочку: ввел ник, нажал "Подключиться", видишь список людей в комнате.
*   **Разработчик 2:**
    *   Пишет черновик WebRTC на фронтенде. Функция, которая запрашивает доступ к микрофону (`navigator.mediaDevices.getUserMedia`).
    *   Пишет логику создания `RTCPeerConnection` в браузере.

#### Этап 2: Интеграция WebRTC (Голос) — Самое важное! (Недели 3-4)
Цель: Соединить WebSockets и Pion. Голосовой чат работает.
*   **Как это работает (Вместе):**
    1. Юзер А заходит в комнату. Фронтенд генерирует *SDP Offer* (описание потока микрофона) и шлет его через WebSocket Разработчика 1.
    2. WebSocket передает этот Offer в Pion (код Разработчика 2).
    3. Pion генерирует *SDP Answer* и через WebSocket шлет обратно юзеру А. Связь установлена!
*   **Разработчик 1:**
    *   Добавляет в WebSocket обработку новых типов сообщений: `webrtc_offer`, `webrtc_answer`, `ice_candidate`. Перекидывает их в модуль Разработчика 2.
*   **Разработчик 2:**
    *   Настраивает `webrtc.NewPeerConnection` в Go для каждого юзера.
    *   **Магия SFU:** Пишет логику "Трансивера" (TrackLocal/TrackRemote). Когда от юзера А приходит `TrackRemote` (его микрофон), сервер добавляет его как `TrackLocal` (исходящий поток) всем остальным участникам комнаты.
    *   Выводит аудио на фронтенде в тег `<audio autoplay>`.

#### Этап 3: Демонстрация экрана (Неделя 5)
Цель: Добавить кнопку "Стрим".
*   **Разработчик 1:**
    *   Добавляет в UI фронтенда кнопку "Показать экран" и сетку для видеоплееров (тег `<video>`).
*   **Разработчик 2:**
    *   По факту, для Pion нет разницы между звуком и видео. Нужно просто разрешить принимать видео-треки.
    *   На фронте добавить вызов `navigator.mediaDevices.getDisplayMedia()`.
    *   Связать пришедший от сервера видео-трек с тегом `<video>` на странице.

#### Этап 4: Продакшен, Деплой и Обход блокировок клубов (Неделя 6)
Цель: Чтобы это работало из любого компьютерного клуба без лагов.
*   **Разработчик 1:**
    *   Пишет `Dockerfile` для Go-бэкенда и `docker-compose.yml`.
    *   Покупает дешевый VPS (в РФ или Европе, главное, чтобы пинг был норм).
    *   Настраивает **Caddy server** или **Nginx** (Caddy проще — он сам получает SSL-сертификаты, а HTTPS для микрофона обязателен).
*   **Разработчик 2:**
    *   В комп. клубах строгий NAT (NAT Type 3/4). WebRTC не пробьется. Нужен TURN-сервер.
    *   Добавляет в `docker-compose` образ `coturn/coturn`.
    *   Настраивает конфиг Coturn (задает логин/пароль) и прописывает эти данные в конфигурацию `RTCPeerConnection` на фронтенде. Теперь, если прямой UDP-трафик заблокирован, голос пойдет через ваш TURN-сервер по TCP/TLS.

### Главные подводные камни (Что нужно знать заранее)

1.  **Управление состоянием (State Management) в Go:**
    В отличие от Python, где GIL, в Go горутины работают реально параллельно. Если два юзера одновременно зайдут в комнату, и вы попытаетесь одновременно записать их в `map` комнаты — сервер упадет с ошибкой `concurrent map writes`.
    *Решение:* Использовать `sync.RWMutex` (блокировки) при любом изменении списка пользователей комнаты, либо общаться с состоянием комнаты через каналы (`channels`).
2.  **Эхо-подавление (Echo Cancellation):**
    В браузере при запросе микрофона обязательно ставьте `echoCancellation: true, noiseSuppression: true`. Иначе вы будете слышать сами себя.
3.  **Потеря пакетов:**
    Если играете в CS2, сеть может нагружаться. В Pion нужно будет настроить NACK (запрос потерянных пакетов) или использовать кодек Opus, который хорошо справляется с потерями.
4.  **Размер комнат:**
    SFU сервер жрет ресурсы процессора пропорционально количеству людей в одной комнате (N * N-1 соединений). Для 5-10 кентов VPS за 300-500 рублей хватит с головой. Если будет 50 человек — придется оптимизировать.
